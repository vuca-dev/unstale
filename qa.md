### 2026-11-04 · OSV lookups did not retry a dropped connection
- Tried: counted `advisories: …: source unavailable` lines against `coverage_stages` events in ingest runs 41825149122 and 41808116070, and bucketed them by time. Ranked the `slice_failed` events in 41825149122. Traced every request the flaky docs test makes (patched http.request and fetch), and ran it 8× with the CPUs oversubscribed 3×.
- Found: OSV was lost for 55/342 (16%) and 27/695 (4%) refreshed technologies. All were `fetch failed` except 2 timeouts. They were spread over the run, densest in the busiest minutes (61 stages → 21 failures), and fast (0.7–5 s). `osvQuery` and `osvVuln` retried only on 429/5xx, never on a network error. All 101 `slice_failed` events have class `Error` (82 new, 14 other, 5 refresh; the same jobs at 44–639 failures), so the class tells them apart from nothing. Docs flake: recurred (run 40763679609, 7437 ms). All 36 of its requests are local, with no fetch and no `gh`. Under load it took 0.5–0.9 s. Not reproduced.
- Chosen: `osvRequest` helper: 3 attempts with back-off on 429, 5xx, network error or timeout; the final error names the cause's code. Regression test with fake timers. PR #209.
- Outcome: OSV network errors are retried. Next run: check the `source unavailable` rate in ingest logs (it was 4–16%) and whether the remaining failures name a cause code.
